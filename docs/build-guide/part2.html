STAGE 11Budgets and the usage ledger IN REPO

Goal. Money is checked before it is spent, at three levels, and every charge is recorded with where the figure came from.
Depends on
Stages 3, 8, 10
Files
packages/core/src/budget.ts
Tables
budget_reservations (held, settled, released), usage_ledger

Build steps

  1. Pricing. pricingFor(models, model) reads prices a module reports; costOf(pricing, usage) charges input and output per million tokens, cache reads at 0.1 of input and cache writes at 1.25.
  2. How much to hold. upperBound is the worst case (whole prompt plus every allowed output token). historicalP90 is the 90th percentile of this step's past costs in this task type when there is enough history. Hold the p90 when known, the upper bound otherwise.
  3. reserve(q, request) runs in a transaction, locks the workspace row, and checks all three limits with money already held counted as spent:
    • the task's own limit,
    • the workspace's monthly budget,
    • the connection's monthly spend limit.
    It throws budget_exceeded with a sentence that says which limit and what to change.
  4. settle(q, id, actual) after the call; release(q, id) when the call failed or was cancelled. A step must never end with money still held.
  5. Ledger row per charge: workspace, run, step, connection, role, module, model, tokens, cost, cost source, reservation.
  6. Estimates before a run. Median and p90 cost and median duration from past runs of the task type, with a confidence level based on how many runs there were and which cost sources they used.

Design notes

  • Reservation is what makes parallel steps safe: two steps cannot both spend the last dollar.
  • The cost source label is cheap to write and is the basis of an honest dashboard.
Done when. Tests show a step refused at each of the three limits, a reservation released on failure, and a ledger row matching the reported usage.

STAGE 12Orchestrator: runs, steps, approvals IN REPO

Goal. Take a task type and a brief, and carry the run to an end: plan what can run, run it within budget, retry, wait for people, recover from crashes.
Depends on
Stages 2, 4, 8, 10, 11
Files
packages/core/src/orchestrator.ts, dto.ts, conclave.ts (the facade that wires everything), test-helpers.ts
Tables
runs, run_steps, approvals, inbox_items

The loop

start()   validate brief and setup -> insert run (copy of the workflow) -> engine.wake -> emit -> audit
advance(runId, signals, heartbeat)          // the engine's handler
  load run + step rows
  recoverInterrupted      rows left "running" by a crash become retries
  applySignals            approvals, answers, outside events
  plan                    which steps are runnable, waiting, done
  if nothing runnable     finish, or go idle / reschedule for a retry or deadline
  else                    run every runnable step in parallel, then loop

Build steps

  1. Start. Validate the brief against the input fields. Check every enabled step has a role with a node, unless the step is optional. Refuse when the month budget is already used. Title the run from the first filled field. Insert, wake, emit, audit, all in one transaction.
  2. Step rows. One row per attempt: step_key, kind, attempt, status, role_key, connection_id, node_label, input, output, error, error_code, tokens, cost, cost_source, latency_ms, idempotency_key (unique), retry_at, round. Statuses: pending, running, waiting, succeeded, failed, cancelled, superseded, skipped, not_taken.
  3. Plan. A step is runnable when every step in its needs is finished in a readable state. Independent steps run together; the DAG decides.
  4. Role step. Check setup, render the prompt, reserve money, mark running, call model.generate with the full NodeCall, stream deltas to the bus, then in one transaction: write the result, the ledger row, settle the reservation, add to the run's cost and call count, emit.
  5. Failure. Map the error; if it is retryable and attempts remain, set retry_at with backoff (default 3 attempts, 1 s, factor 2) and reschedule. Otherwise fail the step; if the step is optional, skip it; else fail the run and put a "problem" item in the inbox.
  6. Guards. Per-run call cap (200) and per-node cap (10) stop runaway loops. Step timeouts abort the call through the signal.
  7. Approval step. Insert an approval and inbox items for people who may decide, mark the step waiting, set the run to waiting. decide(approve | reject | changes) writes the decision and sends a signal. "Changes" stores the note as feedback, supersedes the affected steps and re-runs only those.
  8. Cancel. Mark the run and its open steps cancelled, release held money, abort in-flight calls through their AbortController.
  9. Finish. The run's output is its output step's output. Put a "result" item in the inbox and resolve open items.
  10. Crash recovery. A row still "running" when the run is next advanced belongs to a dead worker: count it as an interrupted attempt and retry with the same idempotency key.
  11. Facade. createConclave({ db, modules, masterKey, ... }) migrates, builds every service and returns them, with startBackground() (engine worker, outbox relay, notifier, health checks) and stop().
  12. Test harness. harness() gives an in-memory instance with the mock model, a Research Brief workspace, and settle() that drains the worker and the relay.
Done when. orchestrator.test.ts covers: a run to approval and to the end; retry then success; failure then inbox item; request changes re-running only what is affected; cancel; budget refusal; recovery of an interrupted step; parallel steps.

STAGE 13Events, outbox and realtime IN REPO

Goal. Every open screen updates by itself, and a dropped connection loses nothing.
Depends on
Stages 3, 12
Libraries
@fastify/websocket (server side, Stage 15)
Files
packages/core/src/events.ts, apps/server/src/realtime.ts, apps/web/src/lib/realtime.ts
Tables
outbox

Build steps

  1. emit(q, topics, event) inserts into outbox inside the caller's transaction.
  2. OutboxRelay polls unpublished rows in id order, publishes each to the in-process EventBus with a rising seq, and marks it published. drain() for tests.
  3. EventBus keeps the last 2,000 envelopes. replay(topics, lastSeq) returns what was missed, or null when the buffer no longer reaches that far.
  4. Text deltas are transient: publishTransient goes straight to the bus and is never replayed.
  5. WebSocket hub: on connect send hello with the current seq. A client subscribes to topics with its last seq. The server checks the caller may see each topic, replays what was missed, or answers refetch.
  6. Web client: one socket, reconnect with backoff, useTopics([...]). Each event is applied straight into the TanStack Query cache (setQueryData) for runs, steps and inbox, and coarser lists are invalidated with a short debounce.

Design note

The bus is in-process, which is right for one container. For more than one, replace the bus with a shared one (Postgres LISTEN/NOTIFY first, NATS at scale) behind the same class. The outbox does not change.

Done when. A test shows an event is published only if its transaction commits, and a client that reconnects with an old seq gets the missed events in order.

STAGE 19Branching, connectors and loops IN REPO

Goal. Workflows decide, not only proceed.
Depends on
Stages 12, 17
Files
packages/contract/src/conditions.ts, the logic step kinds in workflow.ts, graph, plan and progressLoops in the orchestrator, Logic.tsx in the editor; design in docs/workflow-logic.md

Build steps

  1. Logic steps (they cost nothing):
    • If / Switch: cases made of rules; first match or every match; Else.
    • AI router (classify): a model picks one of your categories; an answer that names none goes to Other.
    • Merge: first input with text, all joined, or a JSON object by step.
    • Text: a template, no model.
    • Stop: end as done with a result, or as failed with a reason.
  2. Connectors between steps: Always; Only if (rules on the output or a JSON field); Otherwise; On failure (taken only after retries are used up, and then the failure counts as handled). A connector can carry an instruction for the next step.
  3. Rules (testCondition): contains, equals, starts with, matches, is empty, number comparisons, on the text or a JSON path. Pure functions shared by server and editor.
  4. Deciding (connectorTaken): each connector is undecided, taken or not taken. A step whose incoming connectors are all not taken becomes not_taken, and that flows downstream. Where branches meet, a step waits for all, any, or the first.
  5. Loops. A loop connector sends work back to an earlier step until rules hold, up to a round limit (1 to 20, default 3). Each round supersedes the last round's rows, and {{loop.index}} and the previous output are available. At the limit, carry on with the last round or fail, as chosen.
Done when. logic.test.ts covers every connector kind, joins, a router picking each output, and loops ending by rule and by limit. Logic steps write no ledger rows.

STAGE 20Workspace steps (sub-tasks) IN REPO

Goal. A workflow can run another workspace's task type, or its own, and carry on with the result. This is what makes workspaces composable.
Depends on
Stages 12, 19
Files
startCall, progressCalls, childFinished, cancelTree, path in the orchestrator; truncateWorkflow in the contract
Columns
runs.parent_run_id, parent_step_id, root_run_id, depth, iteration

Build steps

  1. The step names a workspace (or "self"), a task type, and inputs as templates. Optional "run up to this step".
  2. Repeat modes: a fixed number of times; once for each item of a list; until the output contains some text.
  3. Permission. The sub-task runs as the person who started the parent, and only if that person may run tasks in the target workspace.
  4. Budget. Each sub-task gets a share of what is left of the parent's limit (after cost, holds and money already committed to siblings). Its cost is added to the parent's step and run when it finishes.
  5. Guards. At most 5 levels deep; at most 100 sub-tasks per task. A workflow may call itself only if the inner run stops before reaching that call; the editor refuses one that never would.
  6. Lifecycle. A child finishing wakes its parent. Cancelling a task cancels everything under it. A child's approval reaches the inbox with the full path, and the parent reports once, at the end.

STAGE 21Agent and Workflow ports IN REPO

Goal. Hand work to an outside agent or workflow engine and wait as long as it takes, across restarts, without holding a worker.
Depends on
Stages 2, 4, 12
Files
AgentPortV1, WorkflowPortV1 in ports.ts; agent and automation steps; startExternal, watch, progressExternal, applyExternal, completeExternal, failExternal, openQuestion, answerAgent, deliverCallback in the orchestrator; routes/hooks.ts; QuestionPanel.tsx; design in docs/agent-workflow-ports.md
Tables
external_callbacks (token hash, run, step, used)

Build steps

  1. Start. Reserve the step's cap, or the connection's prices (per call plus per minute) over the whole timeout. Call startRun or trigger. Write the handle or execution into the step's input as the checkpoint. Mark the step waiting and return; the worker is free.
  2. Agents. A watcher in the worker process reads streamEvents. Progress lines are written to the step (last 20 kept, flushed at most once a second). A question, the result or a failure goes through an engine signal, so the run's own worker applies it under its lease.
  3. Questions. needs_input opens one inbox item of kind "question" with the full path. The answer is sent with provideInput and the watch resumes. The same question seen again is not asked twice. A step may instead be set to fail on questions.
  4. Workflows. If trigger returns "running", poll with backoff from 2 s to once a minute, or wait for a callback. The callback URL carries a 256-bit token; only its hash is stored and it works once.
  5. Restarts. Waiting steps are re-checked every 30 s. A worker that restarted picks the watch up again; the port contract requires streamEvents to work on a run already under way and to yield a finished run's final event again.
  6. Cost. Charge what the system reports ("reported"), else the connection's prices for the time taken ("estimated").
  7. Ending. A timeout asks the outside system to stop and frees the held money. Cancel does the same; where a system cannot cancel, its result is ignored. Outside runs are not retried unless the step asks, because they are not idempotent.
  8. UI. The task panel shows "working outside" with the latest progress lines, the outside id, and the question box. The Team tab picks a skill or a workflow as the node.
Done when. external.test.ts covers: an agent run to the end; a question and its answer; fail-on-question; a restart in the middle; timeout with release; cancel; On failure catching it; polling; a callback that works once.

STAGE 22Module protocol and the docks IN REPO

Goal. The same module code runs inside the server, on its author's server, as a process the server starts, or on someone's computer. Only the transport and the security boundary differ.
Depends on
Stages 5, 8, 21
Libraries
node:http, node:child_process, node:readline, node:crypto. No dependency added
Files
packages/module-sdk/src/cmp.ts; modules/remote-dock, modules/sidecar-dock, modules/webhook-workflow, modules/sample-agent; apps/server/src/docks.test.ts

The Conclave Module Protocol (CMP 1.0)

CMP is the contract between Conclave and its modules. It is JSON-RPC 2.0, which is a message format and not the point. Do not position it against MCP or A2A; those are adapters that sit behind ports.

DirectionMethods
Host to moduleinitialize (answers with the manifest), health, outsideVersion, discover, model.listModels, model.generate, tool.listTools, tool.call, agent.listSkills, agent.startRun, agent.events, agent.provideInput, agent.cancel, workflow.list, workflow.trigger, workflow.poll, workflow.callback, workflow.cancel, and the $/cancel notification
Module to host (stdio)host.fetch (network calls pass the host's allow-list), host.log

Build steps

  1. Dispatcher. createDispatcher(module) turns method names into port calls, tracks in-flight calls for $/cancel, and encodes errors with the contract code and retryable.
  2. Agent events over request and response. agent.events is a long poll over a cursor (up to 20 s), so one method works over HTTP and stdio.
  3. Serving. serveHttp(module, { secret }) and serveStdio(module) serve any defineModule module unchanged.
  4. HTTP signing. Every request carries a timestamp, a nonce and v1=HMAC-SHA256(secret, "ts.nonce.body"). Refuse requests older than five minutes, a nonce seen in the last ten, and secrets shorter than 32 characters. Sign every answer over the request's nonce. Plain http only for loopback.
  5. Host side. httpClient, spawnClient and cmpInstance give core an ordinary ModuleInstance. The version is checked at initialize.
  6. Remote dock (conclave/remote): URL, shared secret, prices.
  7. Sidecar dock (conclave/sidecar): a command the server starts without a shell and with a bare environment (no keys, no database URL). Only commands listed in CONCLAVE_SIDECARS may start. The module's fetch goes through the host. For real isolation make the command a container with no network.
  8. Docked modules. Testing a docked connection asks its module for its manifest, stores the ports it provides (so role pickers offer only fitting connections), and says so when a later test finds a different module, version or wider egress.
  9. Webhook workflow dock (conclave/webhook-workflow): POST the inputs as JSON; in "wait" mode the response is the result, in "callback" mode the workflow posts to the callback URL. With a secret, sign the request with HMAC. This already works with n8n, Zapier, Make, Activepieces and Windmill, with no module code.
  10. Sample agent: a module made only with the public SDK (two skills, two workflows) to use as a template and as the test target for every dock.
Trust. A signature shows where a package came from and that it was not changed. It does not show the module is safe. The host must still enforce permissions, egress, resource limits and secret isolation for every dock.
Done when. docks.test.ts runs the sample agent through the remote and sidecar docks end to end, and shows a bad signature, a replayed nonce and an unlisted sidecar command are refused.
