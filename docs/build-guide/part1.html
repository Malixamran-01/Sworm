Part A

Before you start

A1 · What Conclave is, and what makes it different

Conclave is a control plane. It does not try to be the model, the agent or the workflow engine. It connects systems that already exist, lets a person compose them into larger tasks, and governs and records the whole run from one place.

The promise to build towards: connect anything that can do work, expose data or raise an event; compose those capabilities into larger systems; control, observe and govern the whole execution from one place.

The six kinds of user in the specification (creator, researcher, developer, operations team and so on) are examples and templates. They are not architecture. One set of primitives serves all of them.

Existing product typeWhat it already does wellWhat Conclave does instead
Agent organisers (Paperclip and similar)Agents as employees: roles, delegation, budgets, approvalsAgents are one kind of node among models, tools, workflow engines and, later, knowledge and devices, all behind one call contract
AI app builders (Dify and similar)Visual workflows, knowledge pipelines, plugins, publishing, inside their own runtimeOrchestrates outside systems where they already run
Durable execution (Temporal)Retries, timers, child workflows, signals, recoverySits above it. The engine is behind an interface; do not rebuild Temporal
Automation tools (n8n, Zapier, Make)Integrations, triggers, branchingEach is a Workflow-port node, called through a webhook dock
MCP and A2AStandard access to tools; standard talk between agentsAdapters into ports. Never compete with them

"We connect anything" is therefore not enough. The difference is five things together:

  1. Capability-level interoperability: unlike systems fit one typed port each.
  2. One invocation and execution model: the same envelope, errors, retries and events for every system.
  3. Limits that hold across nested calls: permissions and budgets only ever narrow as work is delegated.
  4. One history: a single trace and a single ledger for a run that crosses systems and workspaces.
  5. Portable workspaces: a composition can be exported, imported and reused.

A2 · The vocabulary you must keep straight

Most architectural trouble in a platform like this comes from blurring these words. Keep each one a separate thing in code.

WordMeaningExample
PortWhat capability is needed. A typed, versioned interfaceagent@1
ProtocolHow the talking happens on the wireA2A JSON-RPC, MCP, CMP
ModuleThe adapter that implements a port for some systemconclave/a2a
DockWhere the module's code runsbuilt-in, protocol, remote, sidecar, bridge
ConnectionOne configured instance of a module, with its own secrets and limits"Research agent (staging)"
NodeOne usable capability a connection exposesa model, a tool, a skill, a workflow
RoleA named seat in a workspace, filled by a node"Researcher"
Workflow / task typeA composition of steps over roles"Research brief"
Run / taskOne execution of a task type"Tidal energy in the North Sea"
StepOne attempt at one piece of a run"Draft, attempt 2"

Installing a module does not create one node. Three connections to three gateways of the same module give three sets of nodes, each with its own permissions and spend limit.

The rule that holds it together: core knows ports and never names a product. A script (scripts/lint-core-names.mjs) fails the build if a product name appears in core.

Dependency order of the packages

contract  ->  db  ->  engine  ->  module-sdk  ->  core  ->  server  ->  web
                                     |                         ^
                                     +-->  modules/*  ---------+      bridge (uses module-sdk only)

Nothing lower may import anything higher. contract has no knowledge of the database; module-sdk has no knowledge of core. That is what lets a module author depend on two small packages only.

A4 · Design techniques used everywhere

TechniqueWhere, and why
Ports and adapters (hexagonal)Ports in contract, adapters in modules/*. Core is testable with a mock module and never changes when a system is added
Contract-first, shared typesOne package of types and zod schemas used by server, web and modules, so the API cannot drift from the UI
Durable state machineA run is rows in Postgres. A worker "advances" it under a lease; anything in flight can be redone after a crash
Lease with SKIP LOCKEDExactly one worker advances a run at a time, without a queue service
SignalsApprovals, agent events and callbacks are written as rows and applied by the run's own worker, so there are no races
Transactional outboxEvery state change writes its event in the same transaction; a relay publishes it. No event without the change, no change without the event
Reserve, then settleMoney is held before a call and settled to the real cost after. A budget is never found out to be blown afterwards
Idempotency keysrun:step:attempt to providers; an Idempotency-Key header on POSTs that start work
Envelope encryptionMaster key wraps per-organisation data keys; data keys encrypt secrets with AES-256-GCM. Destroying a data key shreds its data, backups included
Default denyModule egress limited to manifest hosts; sidecars off unless listed; bridge targets added only on the device; every API route must declare a guard
Capability narrowingA child call gets a subset of its parent's permissions and a share of what is left of its budget
Normalised errorsEleven error codes with a retryable flag, so retry behaviour is the same for every system
Expand-then-contract migrationsForward-only SQL; add first, remove later, so a rolling deploy never breaks
Tenant column everywhereEvery row has org_id and every query filters on it
Conformance over trustA module is accepted because it passes the kit, not because of who wrote it
One database for two profilesA small query interface over PGlite (no server needed) and node-postgres. The same SQL runs on both, and tests run on both
W3C trace contextEvery outside call carries a traceparent whose trace id is the top task

A5 · Rules for every stage

  • Build in the order given. Each stage only uses what earlier stages made.
  • Finish means tested. Each stage ends with a "Done when" box. Write those tests before moving on.
  • Keep the three checks green: npm run typecheck, npm test, npm run lint:core-names.
  • Do not add a port, a dock or an engine until a real integration needs it. Each one is a contract, a test suite and a security surface.
  • Audit before rebuilding. If the repository already has a stage, check it against this guide and fill gaps; do not rewrite it.

Foundation

STAGE 1Monorepo and toolchain IN REPO

Goal. One repository where every package is TypeScript source, with no build step between packages, and one command each for tests and type checks.
Depends on
Nothing
Libraries
Node 22 or newer · npm workspaces · TypeScript 6 · tsx 4 (runs TypeScript directly) · Vitest 5
Files
package.json, tsconfig.base.json, tsconfig.json, vitest.config.ts, .gitignore, .dockerignore

Build steps

  1. Root package.json: "type": "module", "private": true, engines.node >= 22, workspaces packages/*, modules/*, apps/*.
  2. Every workspace package exports its source: "exports": { ".": "./src/index.ts" }. The server runs with node --import tsx, so nothing is compiled between packages. This keeps the edit-run loop short and removes stale-build bugs.
  3. tsconfig.base.json: strict mode, noUncheckedIndexedAccess, exactOptionalPropertyTypes, ES2023 target, bundler module resolution. Strictness is cheap now and expensive to add later.
  4. Root tsconfig.json includes packages/*/src, modules/*/src, apps/server/src, apps/bridge/src. The web app has its own tsconfig because it needs DOM types and JSX.
  5. vitest.config.ts: include **/*.test.ts under packages, modules, server and bridge; 30 s timeouts; pool: "forks" because each test file starts its own in-memory database.
  6. Scripts: dev:server, dev:web, start, build:web, test, typecheck (two tsc runs), lint:core-names, test:pg, test:a11y.
  7. Write scripts/lint-core-names.mjs now: it scans packages/core/src and fails if a product name (a provider, an agent product, a workflow tool) appears. Running it from day one is what keeps core generic.
Done when. npm install, npm test and npm run typecheck pass on an empty package.

STAGE 2Contract package IN REPO

Goal. The shapes everything else agrees on: the call envelope, the ports, the workflow schema, events and API types. This is the most important package to get right, because every other one depends on it.
Depends on
Stage 1
Libraries
zod 4 (schemas and validation) · uuidv7 (ids that sort by time)
Files
packages/contract/src/: call.ts, ports.ts, workflow.ts, conditions.ts, events.ts, api.ts, index.ts

Build steps

  1. Ids. Export newId() from uuidv7. Time-ordered ids give free ordering, good index locality, and paging by id.
  2. The call envelope (call.ts). Every node, whatever serves it, receives a NodeCall and answers with a NodeResult. 
    interface NodeCall {
  callId; runId; parentCallId; depth;        // where in the nest
  nodeId; input: { text?, data?, files? };   // what to do
  outputSchema?;
  budget: { usd, tokens?, deadline? };       // most it may spend
  permissions: string[];                     // "call:node:<id>"; children get a subset
  trace: { traceparent };                    // W3C, trace id = top task
  idempotencyKey;                            // run:step:attempt
}
  3. Errors. Eleven codes: auth, rate_limited, invalid_request, not_found, timeout, unavailable, refused, cancelled, budget_exceeded, loop_detected, internal. A NodeCallError class carries the code and retryable (true by default for rate_limited, timeout, unavailable). toNodeError(err) maps anything thrown, including AbortError to cancelled.
  4. Usage and cost source. Usage { inputTokens, outputTokens, costUsd, costSource } where the source is metered | reported | reconciled | estimated. Recording where a number came from is what later lets Insights say how exact the spend is.
  5. Trace helpers. traceIdOf(rootRunId) and traceparent(rootRunId, callId). The span id uses the last 16 hex characters of the call id, because the start of a UUIDv7 is a timestamp and could repeat.
  6. Ports (ports.ts). List all twelve names so manifests can declare them (model, agent, workflow, tool, knowledge, trigger, channel, device, storage, media, identity, secrets), but give interfaces only to the ones you implement. A PortRef is name@major. CallContext is { call, signal, emit }.
    • ModelPortV1: listModels(), generate(req, ctx).
    • ToolPortV1: listTools(), call(name, args, ctx). Tools carry sensitive.
    • AgentPortV1: listSkills, startRun, streamEvents, provideInput, cancel. Add in Stage 21.
    • WorkflowPortV1: listWorkflows, trigger, optional poll, callback, cancel. Add in Stage 21.
  7. Workflow schema (workflow.ts). A zod discriminated union of steps by kind. Start with role and approval; later stages add tool, branch, classify, merge, text, stop, workspace, agent, automation. Shared step fields: key, needs (the DAG), optional, disabled, timeoutMs, retry. Also export validateBrief, edgesOf, downstreamOf, portForStep.
  8. Events (events.ts): run.updated, step.updated, step.delta, inbox.updated, notification, each in an envelope with a per-instance seq and topics (user:<id>:inbox, workspace:<id>:runs, run:<id>).
  9. API types (api.ts): every DTO the REST API returns. The web app imports these, so a changed field is a compile error in the UI.

Design notes

  • Standardise the envelope, not each system's behaviour. A model, an agent and a workflow engine keep their own port; they share the call, the error and the usage.
  • A port must not force meaningless methods on a module. That is why agents get startRun and events while a tool only gets call.
  • Handles returned by long-running ports must be plain JSON, because they are stored in a checkpoint and read back after a restart.
Done when. workflow.test.ts covers schema parsing, cycle detection and brief validation. No file in this package imports anything but zod and uuidv7.

STAGE 3Database layer IN REPO

Goal. One small query interface that works the same on an embedded database and on a Postgres server, plus migrations.
Depends on
Stage 1
Libraries
pg 8 (node-postgres) · @electric-sql/pglite (Postgres compiled to WebAssembly, for the Lite profile and tests)
Files
packages/db/src/index.ts, migrations.ts

Build steps

  1. Define Queryable { query<T>(sql, params) } and Db extends Queryable { kind, tx(fn), close() }. Core writes plain parameterised SQL against this. No ORM: the SQL is the same on both backends, and locks (for update, skip locked) stay visible.
  2. createDb(url): pglite:memory, pglite:<dir>, or postgres://. For Postgres use a pool of 10 and an optional schema set through search_path on every connection.
  3. createTestDb(): in-memory PGlite by default; when CONCLAVE_TEST_DATABASE_URL is set, a fresh schema per test on real Postgres, dropped on close. This is how the same suite runs on both.
  4. Helpers: num() (numerics arrive as strings), iso(), json() (send JSON as text and cast with ::jsonb).
  5. migrate(db): a migrations array of { id, sql }, applied in order inside a transaction, recorded in a table. Forward-only. Never edit a migration that has shipped; add a new one.
  6. Money is numeric(14,6), never a float. Times are timestamptz. Every tenant table has org_id.

The tables themselves are added by the stage that needs them; Appendix X2 lists them all with the migration they belong to.

Done when. A test migrates an in-memory database, runs a transaction that rolls back on a throw, and the same test passes with npm run test:pg.

STAGE 4Durable execution engine IN REPO

Goal. Guarantee three things and nothing more: only one worker advances a run at a time; work survives a crash; timers and signals wake runs. Workflow meaning stays in core.
Depends on
Stages 2, 3
Libraries
None beyond the db package
Files
packages/engine/src/index.ts
Tables
engine_tasks (one "advance" row per run: available_at, locked_until, locked_by, generation, attempts), engine_signals

Build steps

  1. The interface: 
    interface ExecutionEngine {
  wake(q, runId, at?)                 // call inside the caller's transaction
  signal(q, runId, name, payload)     // deliver and wake
  forget(q, runId)
  startWorker(handler, opts): EngineWorker
}
type AdvanceHandler = (runId, signals, heartbeat) => Promise<AdvanceOutcome>
type AdvanceOutcome = { kind: "idle" } | { kind: "reschedule", at: Date }
  2. Claim. One statement selects a due task for update skip locked, sets locked_until = now() + lease and locked_by. Expired leases are due again, which is the whole crash-recovery story.
  3. Heartbeat. The handler calls heartbeat() during long steps to extend the lease.
  4. Generation. wake bumps generation. After the handler returns "idle", delete the task only if the generation is unchanged; otherwise something woke the run meanwhile and it must run again. This closes the lost-wake-up race.
  5. Signals. Read unconsumed signals when claiming, pass them to the handler, mark them consumed in the same transaction as the handler's effects.
  6. Worker. A polling loop with a concurrency limit; tick() and drain() for tests (autoStart: false), so tests are deterministic and need no sleeps.

Design notes

  • This is deliberately the smallest engine that is correct. It needs only Postgres, which is what the Lite profile promises.
  • Keep it behind the interface. When scale needs Temporal, write a second implementation; core does not change. Do not make a queue such as BullMQ the only engine: it would tie Lite to Redis.
  • Define execution meaning once, in core, independent of the engine: at-least-once step execution, made safe by idempotency keys and by recording each attempt.
Done when. Tests show: two workers never run one run at once; a task whose lease expired is picked up; a wake during a handler causes one more advance; a signal reaches the handler exactly once.

STAGE 5Module SDK and conformance kit IN REPO

Goal. Everything a module author needs, in one small package: how to declare a module, what it is given, and a test kit that says whether it behaves.
Depends on
Stage 2
Libraries
zod 4
Files
packages/module-sdk/src/: manifest.ts, index.ts, conformance.ts (later: cmp.ts, bridge-protocol.ts)

Build steps

  1. Manifest schema (zod). The install screen, the egress allow-list and the secret store are all driven by it. 
    id          "publisher/name"
version     semver
name, description
ports       ["model@1", ...]            at least one
docks       ["built-in"|"protocol"|"remote"|"sidecar"|"bridge"]
config      [{ key, label, type: string|url|secret|number, required, placeholder, help, default }]
permissions { egress: [host | "{config.key}" | "{config.key[]}"], secrets: [key] }
sensitiveActions, outsideVersions, nodeUi { icon, colour }, reference
  2. defineModule({ manifest, create }) validates the manifest at load time, so a mistake stops the server at start, not at first use.
  3. ModuleContext, given to create once per connection: non-secret config, decrypted secrets for this connection only, an egress-checked fetch, a log, and the connection { id, orgId }. A module must use ctx.fetch, never the global one.
  4. ModuleInstance: ports, health(), optional outsideVersion(), discover(), dockedModule(), close().
  5. Helpers: httpError(status, message) maps HTTP statuses to contract errors; statusForError maps errors to a connection status; requireString; secretKeys(manifest); declaredPorts(manifest).
  6. Conformance kit (runConformance(module, options)). For each declared port it checks: lists return the right shape; a call completes; errors use contract codes; cancellation through the signal works; for long-running ports, handles survive a JSON round trip and watching a finished run again yields its final event. It returns named checks with pass or fail, and takes a fake fetch so tests need no network.
Done when. A ten-line module passes the kit, and a module with a bad id fails at defineModule with a readable message.

STAGE 6Secret vault IN REPO

Goal. Keys are encrypted at rest, never returned by the API, and can be destroyed for good.
Depends on
Stage 3
Libraries
node:crypto only
Files
packages/core/src/secrets.ts
Tables
data_keys (per organisation, wrapped), secrets (ciphertext)

Build steps

  1. A 32-byte master key from CONCLAVE_MASTER_KEY, or generated into <data dir>/master.key with mode 0600.
  2. Each organisation gets a random data key, stored wrapped by the master key.
  3. store(q, orgId, values) encrypts a JSON object of secret values with the data key using AES-256-GCM (random 12-byte nonce, auth tag kept) and returns the row id. open(q, secretId) decrypts.
  4. seal and unseal for secrets that belong to a person, not an organisation (a TOTP seed).
  5. shred(orgId) marks the data key destroyed. Everything it encrypted is unreadable, including copies in backups.
  6. Rule for callers: decrypt for one call, keep the values out of logs, errors and responses.
Done when. Tests show a round trip, that tampered ciphertext fails, and that after shred nothing can be read.

STAGE 7Accounts, roles and access IN REPO

Goal. Know who is calling, in which organisation, and what they may do, in a workspace or outside one.
Depends on
Stages 3, 6
Libraries
node:crypto (scrypt for passwords, SHA-256 for token hashes) · @simplewebauthn/server (passkeys) · qrcode (TOTP setup)
Files
packages/core/src/: errors.ts, access.ts, accounts.ts, mfa.ts
Tables
orgs, users, memberships, identities, sessions, api_tokens, invites, workspace_members, user_totp, recovery_codes, passkeys, auth_challenges, audit_log

Build steps

  1. Errors. ConclaveError(status, title, detail, errors) with helpers notFound, invalid, conflict, budgetBlocked (402). The server turns these into RFC 9457 problem details.
  2. Actor and Principal. Actor { orgId, userId } for services; Principal adds role, scopes, via: session | token.
  3. Roles and permissions. Four roles, each a superset of the one before:
    RoleAdds
    Viewerworkspace:read, connection:read
    Runnertask:run, approval:decide
    Editorworkspace:edit, connection:manage
    Ownermember:manage, org:manage
  4. Access. workspaceRole(q, principal, workspaceId) returns the per-workspace override if there is one, the organisation role otherwise, "owner" for a person's own personal workspace, and null for someone else's. ensure() throws 404 when a workspace is invisible and 403 when the permission is missing. A token's scopes narrow further; a token can never do more than its maker's role.
  5. Accounts. Owner setup; email and password; sessions (a random cookie value, only its hash stored, 30-day expiry); invites (hashed token, optional fixed email); personal access tokens with a cnc_ prefix and scopes; switching organisation; allowed sign-up domains.
  6. Outside sign-in. signInWithIdentity(provider, subject, email) links by provider and subject, and by verified email if allowed. The provider code lives in the server (Stage 15).
  7. Second factors. TOTP with single-use recovery codes (hashed), replay protection by remembering the last accepted step; passkeys through WebAuthn for sign-in and as a second step. A correct password with a second factor returns a short-lived ticket, not a session.
  8. Audit. audit(q, actor, action, target, detail) writes one row. Call it in the same transaction as the change, for every change. The reading side comes in Stage 27.
Done when. accounts.test.ts and mfa.test.ts cover setup, sign-in, invites, token scopes, role overrides, private workspaces, TOTP replay and recovery codes.

STAGE 8Module registry and connections IN REPO

Goal. Turn "a module is installed" into "a configured, tested, limited connection whose nodes can be listed and called".
Depends on
Stages 5, 6, 7
Files
packages/core/src/modules.ts, connections.ts
Tables
connections (name, module id and version, dock, config, secret id, status, spend limit, disabled, later: ports and remote manifest)

Build steps

  1. ModuleRegistry. install(module, source), get(id), has(id), list() returning ModuleDto with config fields, permissions and source ("built-in" or "installed").
  2. Egress. allowedHosts(manifest, config) resolves {config.key} to the host of that URL setting and {config.key[]} to a comma-separated list. egressFetch wraps fetch and refuses any other host with a message that names the module and the host.
  3. ModuleRuntime. One live instance per connection, keyed by a stamp of its config; rebuilt when the connection changes and closed on eviction. Caches model, tool, skill and workflow lists for ten minutes.
  4. Connections service.
    • create: validate values against the manifest's config fields (required, URL shape, number), split secret fields into the vault, store the rest as config, write an audit row.
    • update, remove (refused while a role uses it), setDisabled (the kill switch).
    • test: build the instance, call health() and discover(), save status, detail and outside version.
    • models, tools, skills, workflows: the nodes a connection exposes.
    • instance(actor, id): what the orchestrator calls to get a live module.
    • checkAll: periodic health checks.
  5. DTO. Never return secrets. Return secretKeys (which fields are set), month spend, and which workspaces use the connection.

Connections to other parts

Workspaces point roles at connections. The orchestrator asks for instances. Budgets read a connection's spend limit. The trace and Insights join on connection id.

Done when. connections.test.ts: secrets never appear in a DTO; a module that fetches an undeclared host is refused; a disabled connection cannot be called; audit rows exist.

STAGE 9First modules: mock, OpenAI-compatible, Anthropic IN REPO

Goal. Prove the Model port with three very different adapters, and get a free model for tests and first-run.
Depends on
Stage 5
Libraries
@anthropic-ai/sdk for the Anthropic module. The other two use only ctx.fetch
Files
modules/mock-model, modules/openai-compatible, modules/anthropic, each with src/index.ts and src/index.test.ts

Build steps

  1. Mock model (built-in dock). Deterministic output from the prompt, a few named models with fixed prices, text deltas through ctx.emit, and prompt keywords that force a failure or a refusal, so retry and error paths can be tested without a network. No key, no cost.
  2. OpenAI-compatible (protocol dock). Config: base URL, optional key, prices per million tokens. listModels from /models; generate streams /chat/completions over server-sent events, emits deltas, reads reported usage, and estimates usage by characters when the server reports none (marking usageSource: "estimated"). Egress is {config.baseUrl}. One module covers OpenAI, Ollama, vLLM, LM Studio, OpenRouter and Groq.
  3. Anthropic (built-in dock, official SDK). Streaming, effort levels, prompt-cache token counts, mapping of refusals to the refused code, and passing the idempotency key. Before writing it, read the current SDK documentation for model ids and parameters; do not rely on memory.
  4. Each module's test runs runConformance against a recorded or fake server, then a few specific checks (headers sent, usage read, errors mapped).
Done when. All three pass the conformance kit. This is the first proof that the port works across unlike systems.

STAGE 10Workspaces, templates and versions IN REPO

Goal. A workspace holds roles (seats filled by nodes), task types (workflows), a budget and a version history, and can be exported and imported.
Depends on
Stages 2, 7, 8
Files
packages/core/src/: workspaces.ts, templates.ts, builder.ts, render.ts
Tables
workspaces, workspace_versions, roles, task_types

Build steps

  1. Roles. key, name, description, instructions, port, connection_id, model, effort. A role is on one port; model holds the node name (a model, a tool, a skill or a workflow id).
  2. Task types. key, name, input_fields, workflow. Input fields define the brief form.
  3. Three ways to create. From a built-in template (start with Research Brief: search, research, draft, approval); from the guided builder (composeWorkspace(answers): the same answers always give the same workspace, and compose previews without creating); blank; or by importing a package.
  4. Saving a task type validates everything: the schema, unique keys, that needs point at real steps, no cycles, roles exist and are on the right port, templates reference real fields and earlier steps. Error messages name the step. Each save bumps the workspace version and stores the manifest in workspace_versions.
  5. Runs keep their workflow. A run copies the workflow at start, so editing never changes a task in flight. Task types still referenced by past runs are archived, not deleted.
  6. Templates (render.ts): {{input.field}}, {{steps.key.output}}, and later {{loop.index}}. Keep it a small, safe substitution, not a general expression language.
  7. Export and import. A package is the manifest without connection ids or secrets; importing asks which connection fills each role.
  8. Listing. list and get return month spend, running and waiting counts, and per-role month statistics; other people's personal workspaces are filtered in SQL.
Done when. builder.test.ts shows determinism; saving an invalid workflow is refused with a named step; export then import gives an equal workspace.
